# 父ASIN/ASIN 综合广告诊断（对客版）

## 目标与适用边界

解决什么问题：运营或 CSM 需要一份**客户看得懂**的父ASIN广告诊断报告——回答「生意怎么样、广告花得值不值、结构哪里乱、AI 托管设得对不对、接下来做什么」。

何时调用：用户提供一个 ASIN 或父ASIN（可指定客户/店铺），要求做广告诊断、销售下滑排查、广告结构优化、AI 托管组设置检查、子体投放取舍中的任意一项。

不适用：
- 只查单个指标、单个活动数据的简单取数请求（直接查询即可，不必跑全流程）。
- 未经授权的客户数据（所有取数必须来自已授权的 SparkX 租户，跨客户取数禁止）。
- 要求直接修改账户配置的请求（本技能只产出诊断与建议报告，不执行任何写操作）。

## 输入

必填：
- ASIN 或父ASIN 编码。
- 客户/店铺归属（用于选择正确的 SparkX 租户连接与 profile）。

可选（有默认值）：
- 对比窗口：默认「近 30 天 vs 前 30 天」，可改 7/14 天。
- 核心关注点：默认全流程；客户明确只关心某一块（如只要 AI 审计）时按需裁剪。

系统可自行取得：广告表现、活动/广告组/商品广告配置、托管组设置与行动空间、自动化规则、操作日志（SparkX MCP，需已连接对应客户）；市场/竞品/关键词/评论/价格（卖家精灵，若已连接）；库存快照（SparkX 实体元数据）。

不能猜测的：ASIN 归属哪个 profile（必须用商品广告数据验证归属，禁止按店铺名/类目猜测）；目标 ACOS（必须取自托管组实际设置）。

## 依赖与权限

必要依赖：
- SparkX AI MCP（连接地址与凭据在私有环境配置，按客户拆分独立连接）——广告数据唯一来源，**不可用估算、市场工具或历史记忆替代**。需暴露 get_user_authorized_context / get_ads_perf / get_entity_metadata / get_operation_log。
- 卖家精灵（SellerSprite）MCP——市场统计、竞品、关键词排名、评论、价格带（不可用时市场章节如实标「数据缺失」，不用其他来源编造）。
- 可生成 HTML 文件的环境。

权限边界：
- 全流程只读（查询广告与市场数据），外加在工作目录生成报告文件。
- 不修改任何广告账户配置、不写业务系统、不对外发送。
- 报告中的建议由客户/运营自行决定是否执行。

## 执行方法

按固定顺序执行，每步产出先核对数字再进入下一步。

### 第 0 步：归属验证（硬门禁，不可跳过）

1. 调 get_user_authorized_context 确认连接与目标店铺，得到 profile 列表。
2. 同站点有多个候选 profile 时，对每个候选调 get_entity_metadata（entity=productAd，filters 用子体 ASIN 列表）：返回行数 >0 才是正确 profile；全部为 0 时停下向用户确认归属。
3. 禁止用活动名模糊匹配代替归属验证（会把同品牌其他产品线的活动混进来，导致整份报告错误）。

SparkX 接口实测特性（缺一会导致结论错误，详见 references/sparkx-fetching-notes.md）：
- productAd 等接口返回中 hasNextPage 可能为空，不能据此判断「没有下一页」；用「返回行数 < pageSize 即止」分页，并按 ASIN 分批传过滤列表（每批约 40 个，过长会被截断或调用失败）。
- get_operation_log 参数格式为 entities + resourceIds；活动级日志看不到目标级/商品级动作，campaign / target / productAd 三个层级都要取。
- 跨源关联注意 ID 类型不一致（字符串 vs 整数），统一转字符串再 join。

### 第 1 步：销售环比与异常定位

- 取整体广告与业务指标两个窗口数据：广告花费、广告销售额、广告订单、ACOS、CPC、CVR、业务销售额、业务订单。
- 判断有无明显下降指标；若有，先排查常见外因（价格变化、断货、类目季节性、Listing 异常），证据不足时保留不确定性。
- 即使没有下降，也要回答「效率是否变差」（花费增速 vs 销售增速、CVR 变化），并用操作日志把变化锚定到具体事件（如人工批量新增商品广告的日期）。

### 第 2 步：子体盘点与库存

- 列出全部子体，解析规格（尺寸/颜色/套装数）为业务语言；汇总每个子体的广告花费、销售、订单、ACOS、业务订单、库存、可售天数。
- 出单集中度：列出贡献主要订单的 Top 子体。
- 库存红绿灯：<10 件红（断货风险）、10-30 黄、其余绿；标出「主力款库存告急仍在加码」和「零库存仍在投」两类问题。

### 第 3 步：市场洞察（卖家精灵）

- 类目统计：价格带分布、评分带分布（评分门槛）、Top 竞品对比（先做配置档位对齐，套装数/尺寸不同的先折算单件价，不做跨档位头对头）。
- 本品关键词的自然排名 vs 广告排名。<b>注意：自然位领先广告位是健康结构</b>——自然单零成本、广告不抢自然位本来就能出的单，对 TACOS 友好，不要把「广告位没跟上」当成问题，更不建议追求"广告自然双占位"。是否对某词加投，只以该词现有匹配的花费/出单/ACOS 数据为准：数据合格的词拎出来单独投精准（小额验证加量），不合格的交给自然位出单。识别大泛词陷阱（高搜索量但购买意图弱的词不加价）。
- **只保留 ≤3 条能直接指导广告决策的洞察**，不做数据堆砌。

### 第 4 步：广告结构盘点 + 重复投放检测

- 分类计数：自动 / 手动-广泛 / 手动-词组 / 手动-精准 / 商品定向 / B2B专项 / 防御，各多少条、各花多少钱；已暂停活动单列建议归档。
- 重复投放检测（三档，颜色高亮）：
  - 红：同一关键词+同一匹配方式被 ≥2 条活动同时投放——逐组列出各活动花费/订单，给「只留主活动、其余加否定」建议；
  - 黄：同一搜索词在 ≥2 条活动里花钱（互相竞价）——按合计花费排序展示 Top；
  - 提示：同类自动活动过多（合理数量约 2-4 条），同一子体同时出现在多条自动活动即为重复买量。
- 混投体检：每条活动中本父ASIN子体数量分布，标出重度混投的活动。

### 第 5 步：子体缩减与结构优化建议（必须给出可复用判断方法）

先给判断方法（详见 references/variant-decision-method.md），再逐条重点活动应用出具体名单。要点：
- 按「尺寸×颜色」分需求层，同层内比较；
- 每层保留效率最好的 1-2 个子体（效率 = 订单量 × ACOS 达标，达标线用其所属托管组的目标 ACOS，未托管的用 25% 参考线）；
- 四类暂停标准：花费超阈值零出单 / ACOS 超上限且非该层唯一在售 / 库存 <10 件 / 新开投放不足 14 天（先限额观察）；
- 每个暂停建议必须带：操作范围（在哪条活动里暂停该子体的商品广告，不是下架）、承接位置、复投条件；
- 面向运营沟通：先说明「暂停的只是广告投放，前台变体照常可买」，给可逆小步试点，不承诺销量不降。
- 结构层面：重复词让路、自动活动收敛、表现好的未托管活动迁入托管组、已停活动归档。

### 第 6 步：AI 托管组审计

- 托管组清单：组名、状态、<b>AI 一级目标</b>（推动增长 / 活动冲量 / 保持订单稳定，后台枚举：1=推动增长、2=保持订单稳定、3=活动冲量、4=旧版增长，需搭配 AI 性格一起判断组使命）、目标 ACOS、实际 ACOS、预算、达标情况（达标绿/远超目标可放量/不达标红）。
- **每个组固定展示全部 13 项行动空间**：按表现调价、分时调价、按广告位调价、B2B 调价、调价幅度限制（含当前幅度值）、分时预算、按表现自动加预算、预算重分配、定向收割、自动否词、暂停定向加否定、暂停商品、暂停活动/广告组。后台未返回的标「未设置」，不得整行丢弃。先放一张「每个行动空间是干什么的、什么时候该开」的速查表。
- 每项开关给建议：建议开启（写明错过的机会，用操作日志佐证，如「预算耗尽被迫下线 N 次」）、保持现状、或需人工核实。
- 人工规则方式核查：查托管组规则（RBA）配置与活动级自动化规则。有规则的必须展示完整参数（范围、条件、动作、上下限、排期）并判断是否有问题；无规则则如实写「当前全部为 AI 自动模式」，不为凑内容虚构规则。
- 用操作日志展示「AI 最近 30 天实际做了什么」作为开关是否有效的证据（开关存在 ≠ 实际执行）。

### 第 7 步：行动计划与报告生成

- 行动计划表：动作、负责人、预期效果、怎么算成功、什么情况撤回（每步可逆）。
- 生成单文件 HTML 报告（内置 CSS/JS，无外部依赖），命名 `<ASIN>_综合诊断报告.html`。

## 输出

必交付：单文件 HTML 诊断报告，结构固定：一页结论（生意如何/广告值不值/最该做的 3 件事）→ 销售表现（含走势图与事件标注）→ 子体与库存 → 市场洞察 → 结构体检（分类表 + 重复投放高亮）→ 优化建议（判断方法 + 逐活动名单）→ AI 托管组审计 → 行动计划。重复投放必须用颜色高亮（红/黄/提示三档，附图例）。

对客写作硬规则（违反即返工）：
- 一切文字从客户/运营视角出发，只写运营看得懂的话；
- 不出现：内部 ID、接口名、字段名、原始 ASIN 编码（子体用「36″ 橡木色」这类业务描述）、技术口径附录、验证清单、操作日志统计明细；
- 术语准确：「商品广告」＝子体×广告组的组合（不是「广告位」）；「广告位」仅指活动层级的位置（搜索顶部/商品页/其余）；SERP 位置写「广告排名」；
- 精简优先：正文保留决定判断的事实，避免堆砌技术明细。

## 验收标准

- 归属验证：目标 profile 经商品广告数据验证（行数 >0）。
- 数字正确：ACOS=花费/销售 手动验算一致；活动级与子体级花费占比差异可解释（共享活动含其他产品线）。
- 全量取数：商品广告、活动、规则、日志均为全量分页结果，无「第一页当全量」错误。
- 行动空间 13 项每项展示且与后台数据一致；AI 一级目标与 AI 性格已展示且与后台一致；无规则则明确写「无规则」，不虚构。
- 重复投放清单每组数字能对上原始数据；高亮三档有图例。
- 判断方法可复用：换一个 ASIN 也能照做，不依赖固定客户、日期或某台电脑的路径。
- 业务判断（目标 ACOS 是否合理、暂停名单是否执行）留给客户确认，报告不越权声称「已优化」。

## 异常与已知限制

- SparkX MCP 未连接目标客户 → 中止并提示接入，禁止用估算/市场数据/历史记忆替代广告数据，禁止输出广告部分为占位的报告。
- 卖家精灵不可用 → 市场章节标「数据缺失」，其余照常。
- 接口调用失败 → 缩小过滤列表分批重试，3 次仍失败如实记录缺口，不编数据。
- 子体×活动交叉花费：SparkX 活动级不支持按商品过滤，逐活动的子体名单基于「活动子体构成 + 子体级表现」推断，报告中注明限制。
- 跨 SKU 归因缺失：缩减子体的收益是假设，需试点验收，报告必须保留此不确定性。
- 多个候选 ASIN 无法判断用户指哪个 → 先问，不擅自批量分析。
