# SparkX 客户报告质量标准

## 目标与适用边界

**解决的问题**：CSM 给客户写的复盘报告常见三类问题。一是只有数字没有结论；二是 AI 与人工的比较口径不对，结论站不住；三是建议写得太虚，客户拿到后不知道谁去做、做到什么程度。本技能给出统一的报告结构和交付前验收清单。

**什么时候用**：
- 写客户的月度、双周、季度复盘或 MBR，SparkX 使用报告，AI 托管效果报告，旺季规划报告。
- 审核别人写好的报告，判断能不能直接发给客户。
- 其他报告技能（月度复盘、使用报告、年度复盘）在写作和交付前都要按本标准执行。

**不适用**：
- 只想查一个数（比如"上周 ACOS 多少"），直接用 SparkX AI MCP 查询即可，不需要写报告。
- 内部绩效考核、续约分配、客户分层等管理类材料。
- 本标准只管报告质量，不授权取数、改广告、发给客户或扩大文档分享范围。

## 输入

| 输入 | 是否必填 | 说明 |
|---|---|---|
| 报告对象 | 必填 | 客户、店铺 / 站点范围、读者（老板、运营负责人或运营团队） |
| 时间窗 | 必填 | 本期和对比期的起止日期、天数 |
| 数据 | 必填（写报告时） | 由配套报告技能通过 SparkX AI MCP 取得；审核报告时，输入是已完成的报告正文和它引用的数据 |
| 业务目标 | 可选 | 客户本期目标（控成本、冲量、旺季备战等）；没有就按"效率与规模兼顾"写，并在抬头注明 |
| 毛利、库存、预算上限、促销计划 | 可选 | 缺失时只给有条件的建议，不能假设已批准扩量 |

已经在对话或材料里给出的信息不要重复问。缺少会改变结论的输入时，最多问 3 个关键问题，同时先完成不依赖答案的部分。不能猜测的事实：合同信息、客户目标、负责人、截止日期、活动日历。

## 依赖与权限

- **外部依赖**：无。本技能是写作与验收方法。
- **配套技能**（同批提交，建议一起安装）：`xnurta-monthly-review`、`xnurta-csm-review`、`xnurta-ybr`。它们负责取数，本技能负责结构与验收。
- **权限**：只读。本技能本身不调用任何工具、不写业务系统、不对外发送。

## 执行方法

1. **定口径**：先确认客户、站点、币种、广告类型（SP / SB / SD 分开写，默认不含 DSP）、本期和对比期、归因窗口、数据截至日。自然月天数不同时，除了总量环比，还要给日均变化。
2. **读蓝图**：写作前读 [references/report-blueprint.md](references/report-blueprint.md)。完整报告默认五章：
   1. 一页看懂（主结论、核心指标、三条重点、需要客户决定的事）
   2. 分店及 AI 表现（采纳程度和效率放在一起看，含同款比较）
   3. 市场与旺季 / 下期计划
   4. 分店具体诊断
   5. 下一步行动表

   附"数据说明与证据"。标题可以按客户情况调整，内容不能被泛泛的总结替代。用户只要简版时可以压缩篇幅，但结论、证据、风险和动作都要保留。
3. **建证据链**：每个关键结论都要能走通"数字和来源 → 解释和限制 → 动作"。聚合、环比、比率用代码重新计算，先对账再写。至少给出一个最强的可比证据，以及一个主要风险或反例（如果实际存在）。不能为了证明 AI 有价值而只挑有利样本。
4. **写行动表**：每条动作写清对象、前提、负责人（未知时写角色 + 待确认）、截止日（新建议写"建议日期，待确认"）、验收指标；重大投放或配置变更还要写停止和回滚条件。
5. **交付前验收**：按 [references/quality-check.md](references/quality-check.md) 逐项自查，修正发现的错误。篇幅长或涉及重大决策的报告，如果有独立审阅能力，就用它对照原始数据复核；没有就如实写"已逐项自检，未经独立复核"。

### 关键底线

- **AI 按实际生效时段归属**。"整月曾开启"不等于全月都算 AI；托管开启前、暂停后的数据不计入 AI 结果。
- **比率重新算**：ACOS = Σ花费 ÷ Σ广告销售，不能平均各行的百分比。分母为 0 标 N/A。
- **同 ASIN 比较也不是随机实验**：只能减少部分差异，还要看广告类型、关键词、广告位、托管时长、样本量。未随机的比较不能写"证明""消除了选择偏差""一定能降 ACOS"。
- **不搬旧数字**：不从旧报告复制新年度的促销日历、截止日、预算比例或承诺。当年日期以官方信息为准，查不到就写"待确认"。
- **缺数据就写缺口**：写明缺什么、影响哪一段、谁在什么时候补；不能编图表、日志次数、登录天数或来源链接。某个维度缺数据不代表整份报告停工。

## 输出

- 一份完整报告（在线文档或 Markdown），按五章结构，带真实生成的图表和行动表。
- 审核场景：一份问题清单，按"必须修改 / 建议修改"分级，每条注明位置、问题、依据和改法。
- 不能只交大纲、模板或一句"已完成"。

## 验收标准

- 数值能勾稽：原始行 → ASIN / 管理方式 → 店铺 → 全部，花费、销售、点击、订单都对得上。
- 比率按分子分母重算；同口径下 ACOS = CPC ÷ (CVR × 客单价) 能闭合，误差小于 0.5%。
- AI 与人工的比较写明了归属口径、样本数和限制，没有因果化表述。
- 每条主要建议都有对象、证据、前提、负责人或角色、日期或启动条件、验收指标。
- 图表来自真实数据，没有补造的趋势线，并且已经嵌入交付物。
- **需要业务人员确认的**：目标 ACOS 的合理范围、预算是否允许扩量、促销节奏、负责人与日期。本技能只能标为"建议"，不能写成已承诺。

## 异常与已知限制

- **数据不全**：交付已验证的部分，在数据说明里列出缺口、影响和补数安排，不编造。
- **用户只要短结论**：可以压缩，但不能删掉风险和前提。
- **审核时发现原始数据对不上**：先列为"必须修改"，不替作者猜正确数字。
- **限制**：本标准不验证数据本身是否正确，只检查报告有没有按正确口径使用数据；业务判断是否合适需要 CSM 或客户确认。

## 测试样例

- **自然提问**：「帮我按标准检查一下这份 9 月复盘能不能发给客户」，附报告正文。
  - **预期**：输出分级问题清单，至少检查比率重算、AI 归属口径、行动表是否有负责人和日期、图表是否真实。
- **自然提问**：「用标准结构给客户写一份 10 月 SparkX 使用复盘」。
  - **预期**：调用配套的取数技能（如 `xnurta-csm-review`），产出五章报告和数据说明。
- **测试状态**：本版本（0.1.0）为 MCP 版重写，**未测试，实际输出待补**。原内部版本的方法已在多份客户复盘中使用过，但那些报告含真实客户数据，没有放入本包。
