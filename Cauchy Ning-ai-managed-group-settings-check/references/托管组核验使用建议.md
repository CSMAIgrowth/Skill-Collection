# 托管组核验 Skill 使用建议
本说明帮助同事选对任务、说清范围和时间；不修改四个技能的判断规则。客户名称、日期及数量均为输入示例，不是固定执行参数。

## 1. 最简单的用法

不需要知道Skill英文名称，也不用自己找组ID、开启时间或计算ACOS。先告诉智能体：**看哪个客户、想查什么、查哪些组、看哪段时间**。能由已授权数据或已有上下文查到的信息，由智能体补齐。

一句话模板：

> 对【客户】的【全部托管组／指定组名】，做【效果检验／当前设置检验／历史设置检验／活动下钻】；时间用【节点前后各几天／明确的两期日期／最近完整期间】，结果给我简短正文和 HTML 看板。

不清楚怎么填时，直接说：

> 我想检查【客户】的托管组，但不知道应该先查什么，请先帮我选检查方式，不要直接扫描。

## 2. 按目的选择任务

| 我想知道什么 | 选择哪项 | 主要产出 |
| --- | --- | --- |
| 托管组这段时间表现有没有变差 | 效果检验（三踩一） | 完成判定数、合格／不合格数及比例、两期订单和ACOS |
| 客户现在的托管设置有没有常见风险 | 当前设置检验 | 实际检查数、风险组数、三类设置风险及调整方向 |
| 效果不合格是否伴随当时的设置风险 | 历史设置检验 | 当时的一级目标、目标ACOS、参考期表现与R1/R2/R3结果 |
| 哪些高花费活动值得进一步检查 | 活动检验 | 合格历史设置组中的最多3个高花费活动及活动级结果 |
| 已有结果，只想看报告或调整排版 | 结果导出／HTML展示修改 | 沿用冻结快照，不重新抓客户数据 |

“设置检验”没有说明当前还是历史，且上下文不能确定时，必须先确认。“历史核验节点”不一定等于“真实开启日”，不能自动混用。效果检验、设置检验、活动筛选与算法责任认定是不同环节。

## 3. 可以直接复制的请求

**效果检验：**

> 对【客户】的【指定名单或明确全部范围】，以【YYYY-MM-DD】为节点，比较节点前后各【N】个完整自然日，执行三踩一检验，排除节点当天。输出合格、不合格及未完成核验数量，并生成 HTML 看板。不修改广告。

**当前设置扫描：**

> 对【客户】当前开启的全部托管组执行当前设置检验，使用最近14个完整自然日，不含当天。汇报实际检查数、去重风险组数和三类风险数量及占比，生成一份含逐组证据的 HTML 看板。

**历史开启设置：**

> 对上一步不合格组核验最近一次开启托管时的设置。请从历史日志查出开启时间、当时成员和目标，参考开启前14天表现，不用当前设置替代。输出三类设置风险及无法还原项。

**指定历史时点设置：**

> 对上一步不合格组，核验【YYYY-MM-DD当地00:00】时的设置，参考此前14天表现。本次检查指定时点，不把它称为真实开启时设置。

**活动下钻：**

> 接着使用上述效果与同历史时点设置快照，仅对效果不合格且三类设置规则均未命中的组，按后期花费取最多3个活动，沿用相同窗口和目标执行活动级三踩一。再比较点击、转化率和CPC；需要搜索词定位时，请在对应指标下列出已取得证据的Top5。

**整套执行并生成HTML：**

> 对【客户／店铺范围】的【托管组范围】，以【日期D】为节点做前后各【N】天效果检验；对不合格组检查同一D时点的历史设置，仍参考D前14天表现；对历史设置三类规则均未命中的组继续检验高花费活动，活动检验沿用效果检验的N天窗口，并比较点击、转化率和CPC。最后按已确认模板生成HTML看板。先说明解析后的对象、日期、N和设置时点，有实质歧义再问我；不要修改广告，也不要把候选写成算法责任认定。

效果检验的N可由用户指定为14、28、30天等正整数；只给节点日期未给N时询问天数，不固定代填14天。历史设置检验的开启前14天参考期独立保持不变。“最近完整30天对比此前30天，排除归因期”也可以作为时间请求，但须先确定店铺当地实际日期和适用归因等待口径。它是两个连续30天窗口，不自动改成某个节点两侧、排除节点当天的窗口。效果比较周期不自动替代设置技能的参考周期。

## 4. 智能体怎样主动引导

在相关技能被调用或已获知本包用途时，以下情况应先阅读本说明并给出简短引导：用户明确说不知道怎么用、只说“帮我检查一下”且目标不明、当前／历史设置有歧义，或所选环节缺少必要上游结果。

推荐开场：

> 这套工具可以查托管组效果、当前设置、历史设置，也可以继续看高花费活动。你想先解决哪一个问题？告诉我客户和检查目标即可，组ID和能查到的时间信息我来核对。

随后只追问当前缺少且影响执行的信息，不要求用户机械填写整张表：

- 客户不明确或多客户冲突：问客户名称，按实时授权核对租户和店铺；不复用其他客户身份。
- 只有客户或“检查一下”：先确认查效果还是查设置，再确定全部组或指定组。不能未经选择就全客户扫描。
- 只说“最近”“挑数据多的时候”：给出适合本次任务的时间选项并请求选择；未经授权不自行选节点、换组或改变窗口。
- 组名或链接可定位：先只读解析唯一对象。重复名称再问店铺，不要求用户自己查内部ID。
- 用户只问方法、审阅或导出技能：提供说明和示例，不运行客户分析。
- 缺活动阶段上游结果：先查本轮是否已有可复用快照；没有则说明缺哪项，并询问是否补做，不直接假定设置通过。

信息足够时，简短说明执行范围后直接继续，不反复弹出教程或要求重复确认。同一缺项只问一次；用户新答复与已有上下文合并使用。

## 5. 执行前让用户知道什么

用一句话或短表列出已解析的客户／店铺、托管组范围、实际起止日期、当前或历史设置时点、参考周期和交付形式。信息已明确时这是执行说明，不是新的确认审批。

没有指定文件形式时，默认交付简短聊天结论和独立 HTML 看板，不再默认导出 Excel，也不要求同时生成内部版和对客版。用户明确需要分享给客户时，另生成只含对客允许字段的 HTML 文件；其他格式仅在用户明确要求时提供。要求整套报告不等于授权改广告、外发或直接判责。

## 6. 读结果时重点看什么

- 效果：扫描多少组、完成多少组、多少不合格；未完成不算合格。
- 设置：多少组存在风险，分别触发哪类规则；三类可重叠，风险不等于已证实设置错误。
- 活动：按花费选择哪些活动、哪些完成判定；暂不能计算ACOS不能硬判，不用第四名递补。
- HTML：是数据快照，不是实时监控；已删除板块不恢复，数据与聊天结论一致。

不要为了凑齐结果绕过窗口未结束、查询失败、零销售或历史配置不足。说明影响范围，保留能独立判断的部分。

## 7. 引导验收场景

| 用户请求 | 期望行为 |
| --- | --- |
| “这个怎么用？” | 给任务选项和一条模板，只问当前必要信息，不查询客户数据 |
| “帮我查jason的设置”且无历史上下文 | 先确认当前还是历史；不默认改成效果检验 |
| “对指定组以某日做前后28天效果检验，生成HTML” | 解析对象、日期和28天窗口后执行，不重复要求已经给出的客户、日期、天数、格式 |
| “效果按30天，设置仍看前14天” | 保留两个不同周期，不强行统一 |
| “把旧报告标签挪一下” | 仅展示修改，不重新拉数据，不新增核验结论 |
| “继续下钻”，但找不到历史设置快照 | 指明缺少的上游结果，询问补做；不将未知设置当通过 |

以上为文字场景审查标准，不代表已经在其他同事的智能体环境完成自动触发验证。
