# Case 分析执行细节参考

本文件承载主 skill 的详细取数、设置日志、场景、截图和洞察句式。主 skill 只保留执行顺序和硬规则；需要生成正式 case 时按需读取本文件。

## top_n_terms

### 5.2.2.1 分层取数与 Top N 扫描策略

下钻取数的目标是形成「最小充分证据集」，不是做广告账户全量审计。必须把「用于计算总体表现的数据」和「用于解释 case 根因的明细数据」分开处理：总体表现需要保证可比和完整，明细解释只抓高影响对象。

推荐使用以下四层扫描路径：

| 层级 | 默认取数范围 | 目的 | 进入下一层的条件 |
|---|---|---|---|
| L0 托管组筛选 | 全部托管组的轻量级汇总：当前周期、对比周期、近 14 天、近 7 天的花费、销售、订单、ACOS、CPC、CVR、目标 ACOS/CPA、创建人、开启时长、行动空间 | 形成问题候选、正向候选和创建人分组 | 只有达到花费/订单门槛、目标偏离或近期趋势异常的托管组进入 L1 |
| L1 广告活动 | 入选托管组内的完整广告活动成员均进入轻量级基础清单和汇总；逐活动核对创建/首次投放、加入托管组、AI 启用、暂停/移出时间，确认至少有 1 个当前已启用活动。当前周期和对比周期再分别取花费 Top 50 的并集，并补充异常对象作为重点分析集 | 保留完整成员及暂停/启用状态变化，并按活动实际纳管期判断哪 1-3 个广告活动解释主要结果 | 只对重点分析集中的高影响广告活动进入 L2 |
| L2 广告组/投放/广告位 | 仅入选广告活动；默认花费 Top 50，或累计覆盖托管组/广告活动 80% 花费的更小集合 | 定位主要低效流量、主要订单来源和结构断点 | 只有需要解释转化、搜索意图或设置动作时进入 L3 |
| L3 搜索词与操作日志 | 搜索词取累计覆盖 80% 花费的集合，最多 Top 50；操作日志只取当前 case 相关对象和相关时间窗口 | 形成「对象-动作-结果-设置」证据链 | 证据已能解释核心指标变化时停止，不继续扩展长尾 |

执行原则：

1. **Top N 是明细扫描上限，不是总体指标口径。** 托管组的 ACOS、花费占比、创建人汇总和周期对比仍应来自托管组级汇总或完整可比人群，不能用 Top 50 明细代替总体 KPI。
2. **先筛选托管组，再带 ID 下钻。** L0 只获取支持筛选的字段；入选后复用托管组 ID、广告活动 ID、广告组 ID，后续查询必须带当前 case 范围，避免再次扫描账户全量。
3. **完整成员纳入，状态只决定托管组是否可被选为 case。** 入选托管组内的全部活动都进入基础清单、花费/销售/订单/ACOS 汇总和结构判断，不能因为不是 Top 50 或当前已暂停就从托管组分析中删除；暂停活动应作为成员/结构变化的一部分说明。正式 case 的前提是该托管组当前至少有 1 个已启用活动；若全组已暂停或已归档，默认不进入 case 候选，除非用户明确要求分析其暂停背景。若广告活动数量较多，可只取活动级轻量指标；广告活动内部的广告组、投放和搜索词明细再按重点分析集下钻。**但成员完整纳入不等于比较窗口相同：新建或中途纳管活动必须按自身有效纳管天数单独切窗，不能继承托管组历史 30 天。**
4. **对比窗口取 Top N 并集。** 当前周期和对比周期不能各自只取 Top 50 后直接比较；应取两个窗口 Top 50 的 ID 并集，并补充「当前花费下降但对比期花费很高」和「当前新进入高花费」的异常对象，避免漏掉从高位跌落或快速放量的广告活动。Top N 并集用于重点分析，不影响广告活动全量基础清单。
5. **按累计花费覆盖停止明细下钻。** 默认先取重点分析集 Top 50；如果 Top 10 或 Top 20 已覆盖该层总花费的 80%，直接停止。若 Top 50 仍未覆盖 80%，不自动扩展到全量，而是补充以下异常集合：高花费 0 单、高点击低转化、ACOS 高于目标、近 7/14 天明显恶化、转化好但没有被单独承接的对象。该规则不适用于广告活动基础清单，广告活动基础清单仍需全量保留。
6. **搜索词按影响权重取数。** 默认只取累计覆盖 80% 花费的搜索词，最多 Top 50；在此基础上强制补充四类例外：高花费 0 单、高点击 0 单、ACOS 明显高于目标、已转化且效率达标但尚未形成手动承接的词。正向 case 不能只看高花费低 ACOS，还要保留高效搜索词，以便沉淀收割和手动承接经验。
7. **广告位优先做三类汇总。** 搜索结果顶部、商品详情页、其余广告位通常足以判断广告位结构，不默认逐行扫描。只有当某一广告位是主要花费来源、近期成本突增或托管组开启了广告位调价时，才继续补充更细粒度数据。广告位表现和系统开关均不代表人工能改系数；要提出人工广告位动作，必须额外取到可编辑入口、权限、当前值与范围。
8. **操作日志不按表现 Top N 截断。** 日志按 case、对象、时间窗口和相关操作类型过滤；默认看近 7/14 天，必要时补 30 天。保留导致指标转折的第一条动作、转折点附近动作和最新动作；如果日志总量很小则全部保留，不能为了凑 Top N 丢掉时间链路。
9. **趋势数据只对候选 case 取。** 账户级日趋势不作为默认全量明细。先用 L0 找到候选托管组，再只取候选组的 7/14/30 天日趋势；如果接口支持按组聚合，优先使用聚合结果，避免拉取全部广告活动逐日明细。
10. **每层都设置最小证据门槛。** 低花费、低点击或订单数过少时，即使 Top 1 覆盖 80%，也只能做线索判断。问题 case 至少应同时满足花费/点击门槛与一个异常信号；正向 case 至少应满足足够订单量、效率达标和连续窗口稳定，避免把随机单量当成可复制经验。
11. **查询结果缓存并复用。** 同一 case 的当前周期、对比周期和近 7/14 天结果应保存在同一数据包中，后续报告生成、复核和重跑只在本地重新聚合，不重复调用明细接口。查询失败时只重试缺失窗口或缺失 case，不重复抓取已成功的全量结果。

推荐的停止条件是：当前层已覆盖 80% 主要花费，且已覆盖主要订单来源、主要效率压力或全部高优先级异常；同时不存在未解释的重大指标变化。满足后停止下钻，并在报告中写明实际覆盖率和补充的异常对象。

推荐的下钻记录格式：

`取数层级：L0/L1/L2/L3｜时间窗口｜当前 case 范围｜Top N 或累计花费覆盖率｜补充的异常集合｜停止原因`

示例：

- `取数层级：L1 广告活动｜当前 30 天与前 30 天｜仅问题托管组｜两个窗口 Top 50 并集｜补充近 14 天花费下降超过 50% 的活动｜已覆盖托管组 92% 花费`
- `取数层级：L3 搜索词｜近 14 天｜仅问题广告活动｜Top 50，累计覆盖 84% 花费｜补充高点击 0 单和达标转化词｜已覆盖主要效率压力`

该策略的核心经验是：**全量只用于建立可比的托管组事实底座，Top N 和累计花费覆盖用于控制明细扫描，异常集合用于防止长尾和跌落对象被漏掉，日志则保留时间链路而不是机械截断。**

### 5.2.3 专业术语中文化

对客报告和复盘正文不要直接使用后台英文枚举或英文专业名。后台字段可用于抓数和识别，但输出时必须转换为中文表达。

常用术语转换：

| 后台字段 / 英文术语 | 报告正文写法 |
|---|---|
| looseMatch | 宽泛匹配 |
| closeMatch | 紧密匹配 |
| substitutes | 同类商品投放 |
| complements | 关联商品投放 |
| campaign | 广告活动 |
| ad group | 广告组 |
| target | 投放 |
| keyword target | 关键词投放 |
| product target | 商品投放 |
| search term | 搜索词 |
| product ad | 推广商品 |
| placement | 广告位 |
| Top of Search | 搜索结果顶部 |
| Product Pages / Detail Page | 商品详情页 |
| Rest of Search / Other | 其余广告位 |
| Sponsored Products / SP | 商品推广 |
| Sponsored Brands / SB | 品牌推广 |
| Sponsored Display / SD | 展示型推广 |

执行规则：

- 第一次出现时优先写中文名，不需要括号补英文；除非用户明确要求核对后台字段，才可写成「中文名，对应后台字段为 xxx」。
- 数据表字段名、截图位、客户表达版本都必须用中文术语。
- 如果英文术语本身是搜索词、广告活动名、托管组名或后台原始字段值，允许保留原文，但分析解释必须用中文术语。
- 对于 ACOS、ROAS、CPC、CVR、CTR、CPA 这类行业常用指标，可保留缩写；客户不熟悉时补中文解释，例如「CVR 转化率」。

## settings_logs_harvest

### 5.3.1 托管组设置变更历史判断

正式 case 必须优先查看托管组 AI 设置变更历史，而不是只看操作日志模块。

重点字段：

| 变更项 | 分析意义 |
|---|---|
| 托管目标 | 判断 AI 当时是偏增长、稳单、控成本还是冲量，影响否定、收割、调价和预算承接倾向 |
| 目标 ACOS / CPA | 判断系统探索边界是放宽还是收紧 |
| AI 人格档位 | 判断动作力度和探索/收缩倾向，档位变化后要单独切窗 |
| 竞价优化 / 按表现调价 / 分时竞价 | 判断 AI 是否有出价调整权限 |
| 广告位调价 | 判断 AI 是否能处理搜索结果顶部、商品详情页、其余广告位的效率分化；系统开关不代表人工可编辑具体系数 |
| 否定定向 | 判断 AI 是否能清理低效搜索词、低效 ASIN 或低效投放 |
| 定向收割 | 判断 AI 是否能把高效搜索词从探索池沉淀到更精准结构 |
| 低效定向暂停 | 判断 AI 是否能暂停长期低效投放 |
| 分时预算 / 动态预算 / 预算重分配 | 判断 AI 是否能解决预算断流和预算迁移 |
| 竞价范围 | 判断 AI 探索边界是否被限制 |
| 托管组新增/移除广告活动 | 判断表现变化是否由结构变更带来 |

判断规则：

- 如果截图或设置历史显示月中从「推动增长」切换为「保持订单稳定」，必须将切换前后分开分析。切换前更可能出现扩流、减少强否定、加速消耗；切换后才适合评价稳单、控本和低效清理是否有效。
- 如果目标 ACOS 从高值下调到低值，例如从 35% 调到 30%，下调后应观察 AI 是否逐步收紧出价、预算和低效流量，不能把下调前的高 ACOS 完全归因给当前目标。
- 如果 AI 人格档位提高，且当前目标是保持订单稳定或控成本，并且否定定向已开放，理论上低效清理力度应更强；若实际否定很少，必须先确认该设置生效时长是否足够、否定权限是否长期开放、是否之前处于推动增长阶段。
- 如果分时预算、预算重分配或动态预算月中被关闭，后续预算断流不能简单写成 AI 预算能力不足，而要写成「预算动作空间被收窄后，AI 可处理范围下降」。
- 所有设置变更都要标注日期，并在结论里说明：该结论适用于变更前、变更后，还是整月汇总。

### 5.3.2 操作日志动作归因

正式 case 必须先给操作日志做动作归因，不能把所有日志统称为 AI 动作。尤其是托管组对应广告活动的操作日志，必须区分「AI 执行动作」和「人工/后台/邮箱/外部平台/自动化规则动作」。

日志口径固定格式：

`操作日志口径：时间窗口｜后台位置/日志模块｜对象范围｜动作类型范围｜按操作来源分组｜是否仅限当前托管组/广告活动`

动作来源分类：

| 来源类型 | 常见识别方式 | 报告写法 | 归因规则 |
|---|---|---|---|
| AI 执行动作 | changedBy / operator / 操作人显示 AI、SparkX AI、Xnurta AI，或明确是托管 AI 自动执行 | AI 动作 | 可用于判断 AI 实际做了调价、预算、否定、收割、广告位等动作 |
| 人工动作 | 操作人是姓名、邮箱、客户账号、运营账号 | 人工动作 | 不能归因给 AI；若改目标、预算、出价、状态，要判断是否打断 AI 学习或改变对比口径 |
| 后台/管理端动作 | 操作来源显示后台、admin、运营后台、内部账号、系统管理员等 | 后台动作 | 视为人工或管理端配置动作，除非字段明确显示为 AI 自动执行 |
| 外部平台动作 | 操作来源显示 Amazon Console、Amazon、平台同步、外部来源等 | 外部平台动作 | 不能归因给 AI；需判断是否为客户在亚马逊后台手动调整或平台同步 |
| 自动化规则动作 | 操作类型或来源显示 rule、automation、自动化规则、按规则等 | 自动化规则动作 | 与 AI 托管分开分析；若与分时预算或按表现调预算冲突，要写成规则影响 AI 动作空间 |
| 来源不明 | 操作人为空、来源字段缺失、只看到动作但无法识别执行方 | 来源待确认 | 不做强因果归因，只作为线索 |

执行规则：

- 每个重点 case 至少汇总两张日志视角：AI 动作汇总、非 AI 动作汇总。
- AI 动作汇总重点看：出价调整、预算调整、预算重分配、分时预算、广告位调整、否定、收割、暂停、预算超限响应。
- 非 AI 动作汇总重点看：人工改托管目标、目标 ACOS、AI 人格、行动空间、预算、出价、广告活动状态、广告位、自动化规则。
- 如果人工或后台在周期中修改了目标 ACOS、AI 人格、行动空间、预算或出价，必须按修改日期切分窗口，不能把修改前后的结果全部归因给 AI。
- 如果人工改竞价后 24 小时内 AI 竞价动作减少或暂停，应标注可能存在冷静期影响。
- 如果人工改预算后当天分时预算异常或未执行，应标注可能存在人工预算修改影响；站点时间 23 点后修改预算可能影响次日分时预算。
- 如果日志里既有 AI 高频调价，又有人工频繁改预算/出价，结论应写成「人机动作交叉，AI 学习和归因被干扰」，不能简单写 AI 调价无效。
- 如果 AI 没有做某类动作，先检查行动空间是否开放；未开放时写成「AI 未被授权执行该动作」，不要写成「AI 没有能力」。
- 如果操作来源是邮箱账号，必须在报告内部判断为人工动作；对客报告可写「人工调整」，不要暴露具体邮箱。
- 如果来源是后台或外部平台，但不能确定是不是客户本人，写「非 AI 调整」或「外部平台调整」，并列为待确认点。
- 操作日志中英文动作名只用于识别，报告正文要转成中文，例如 DailyBudget Increased 写「预算上调」，Keyword Bid Decreased 写「关键词出价下调」，Negative Keyword Added 写「添加否定关键词」。

输出建议：

- 在单 case 中使用「操作日志归因」小节，先写日志口径，再分别写 AI 做了什么、人工/后台/外部平台做了什么、这些动作如何影响结果。
- 如需表格，字段建议为：时间窗口、动作来源、动作类型、次数或关键记录、影响判断、是否改变结论口径。
- 对客户表达时，不要写成追责口吻；写成「这段表现同时受到 AI 自动动作和人工设置调整影响，所以需要按调整时间切分判断」。

### 5.3.2.1 设置与日志深度诊断硬规则

设置与日志分析不能停在「开了哪些功能、做了多少次动作」。每个重点 case 必须依次回答：

1. 托管目标、生命周期和客单价决定了这组要解决什么问题。
2. 当前目标 ACOS/CPA、AI 人格、竞价范围和行动空间，允许 AI 对哪些对象做什么。
3. 周期内实际发生了哪些 AI、人工、后台、外部平台和自动化规则动作，是否有时间、对象、前值和后值。
4. 动作是否发生在指标拐点之前，动作后 7/14/30 天哪个窗口出现了响应。
5. 结果不佳究竟属于未授权、已授权但未见执行、动作方向不匹配、商品/市场承接问题，还是人机动作交叉。

设置变更历史和操作日志必须分开取证：前者回答「当时允许什么」，后者回答「实际做了什么」。每个 case 至少输出一张「设置项｜生效时间｜理论可执行动作｜实际动作｜结果信号｜诊断」表；只有次数、没有对象/前后值/时间的日志，只能作为动作数量线索，不能作为完整执行证据。

详细的目标-行动空间匹配、日志时间对齐、常见缺口诊断矩阵和资料喂法，见 `references/settings_action_log_reasoning_playbook.md`。
正式报告生成后，使用 `scripts/case_preflight.mjs` 做日期、名称、必需表格和默认环比口径预检；该脚本只做校验，不改变报告内容。

### 5.3.3 定向收割能力边界

正式 case 里不能把「开启定向收割」写成万能动作。定向收割条件较苛刻，必须同时判断来源数据、承接结构、预算和重复投放风险。

收割判断前先确认：

1. 来源侧是否有足够搜索词数据，且搜索词表现稳定，不只是小样本偶然出单。
2. 目标侧是否存在可承接的手动广告活动、广告组或投放结构，且匹配方式、预算、目标 ACOS 与该词意图适配。
3. 该搜索词是否已在其他结构中存在，是否会造成重复投放或预算内耗。
4. 是否设置了不收割关键词、品牌词保护、型号词保护或客户不希望新增的词。
5. 目标广告活动是否有预算承接能力；否则即使收进去，也可能因为预算不足无法放量。

自动广告 case 的特殊规则：

- 自动广告没有投放词，只有自动投放类型和搜索词结果；如果托管组内只有自动广告，不能写成「开启定向收割即可把词收进来」。
- 对自动广告里跑出的高效搜索词，只能先写为「手动承接候选词」或「需要人工新增投放词的线索」。
- 若要把自动广告的高效搜索词沉淀为精准匹配或词组匹配，通常需要先人工创建或确认已有手动承接广告活动/广告组，再把高效搜索词作为投放词加入，之后再让 AI 在已授权范围内做调价、预算、否定和后续收割判断。
- 若没有手动承接池，AI 能做的主要是自动投放出价、预算、广告位和否定等优化，不能把「未收割」直接归因为 AI 执行失败。
- 因此，自动广告问题组的 todo 优先写「确认/补齐手动承接结构 + 人工加入高效搜索词 + 观察 7-14 天」，不要直接写「开启收割」。

对客表达建议：

- 不写「高效词还没被 AI 收割」。
- 改写为「自动广告已经跑出可承接的搜索词线索，但当前缺少适合承接这些词的手动投放结构，需要先补承接池，再观察 AI 是否能继续优化」。

### 5.4 再按场景判断

不同场景不能套同一把尺。

| 场景 | 判断重点 |
|---|---|
| 新品 | 不宜过早判 AI 失败，先看是否获得点击、收割词、建立相关性 |
| 成长期 | 看放量是否带来订单和排名信号，ACOS 要有护栏 |
| 成熟期 | 看 CPA/ACOS 是否稳定下降，预算是否从低效流量迁移 |
| 清货 | 看 CPA 底线、库存消化、止损是否明确 |
| 大促/旺季 | 看关键时段承接、预算利用、促后目标是否收回 |
| 礼物品类 | 礼物词和产品词拆开看，礼物词决策链更长 |
| 多变体 | 判断是否因价格带、搜索意图、生命周期混组造成预算冲突 |
| SB/SD/DSP | 不只用 last-click ACOS 下结论，必要时降级为「站内直接归因偏弱」 |

### 5.4.1 转化路径与窗口选择

7/14/30 天不是每个 case 都必须完整展示的固定模板。先判断客单价、历史转化延迟和购买决策路径：

- 短链路、低客单价：30 天判断整体结果，14 天确认趋势，7 天可作为近期预警。
- 中链路：30 天判断结果，14 天判断趋势；7 天只有在问题明显或用户要求时补充。
- 长链路、高客单价：30 天为主，14 天作为辅助；7 天只用于动作是否落地或明显风险，不用于单独判断 AI 成败。

报告必须说明为什么选择或不展示某个窗口，不能为了格式统一强行切三个周期。

## action_space_details

### 7.1 AI 托管能力边界

分析时必须区分「AI 能做什么」和「客户愿不愿意付出调整成本」。

做正式 case 前，必须读取 `references/sparkx_ai_managed_logic.md`，并用其中的托管目标、AI 人格、竞价、预算、广告位、否定、收割和人工介入边界判断 case。下表只保留最常用的行动空间边界。

| 行动空间 | AI 能力边界 | 常见误判 |
|---|---|---|
| 竞价优化 / 按表现调价 | 能基于表现调整出价，但受目标 ACOS、竞价范围、人格和数据量限制 | 只看出价次数，不看目标和范围是否允许有效变化 |
| 分时竞价 | 能按时段调整竞争力，但不能解决搜索词意图错误 |
| 广告位调价 | 能处理不同广告位效率差异 | 未核验可编辑入口、权限、当前系数和范围时，却建议人工或 AI 按固定比例压商品详情页流量 |
| 否定定向 | 能清理低效搜索词、低效 ASIN 或低效投放，但倾向受托管目标和生效时长影响 | 看到否定次数少就直接判 AI 没清理，忽略此前可能是推动增长目标 |
| 定向收割 | 在有合适承接结构、足够数据、预算和去重条件满足时，能把高效搜索词沉淀为更精准投放 | 对只有自动广告的托管组，直接建议开启收割并期待 AI 自动收词 |
| 低效定向暂停 | 能暂停长期低效投放，但属于高影响动作，需要客户接受止损边界 | 在未开放暂停时要求 AI 停掉低效投放 |
| 分时预算 / 动态预算 / 预算重分配 | 能处理时段预算、预算承接和组内迁移 | 预算动作关闭后仍把预算断流归因给 AI 没做事 |
| 结构优化 | 能辅助结构调整，但新增托管组、拆组、重建活动通常涉及客户确认和行动成本 | 轻易建议重建或新增托管，忽略客户操作成本 |

当前已知高层规则：

- 「推动增长」目标更偏扩流与拿量，否定和收缩动作通常更谨慎，容易出现泛流量进入和花费加速。
- 「保持订单稳定」目标更强调订单承接与效率平衡，在否定定向开放且生效时长足够时，应更关注低效清理是否跟上。
- 「降低 ACOS / 控成本」目标更适合严格降价、否定、低效暂停和预算迁移，但目标一次收太紧可能导致订单断层。
- AI 人格档位会影响动作力度；档位变化后必须单独观察，不用变更后的档位解释变更前动作。
- 以上是诊断层面的高层规则；如果需要精确到各动作触发阈值、否定概率、人格档位内部算法，必须读取客户提供的产品资料后再沉淀。

## insight_phrases

## 9. 标准洞察句式

### 9.1 正向 AI Case

- 这个 case 的价值不只是 ACOS 下降，而是 AI 在目标边界内把预算更快集中到已有转化信号的流量上。
- 当前表现属于健康放量：花费承接增加的同时订单同步增长，ACOS 没有明显失控。
- 这组适合作为可复制 case，因为数据改善、托管设置和操作日志能互相印证。

### 9.2 问题 Case

- 这个 case 不适合作为正向案例，更适合作为设置修复案例：当前问题集中在目标 ACOS 和行动空间不匹配。
- ACOS 上升不能直接等同于 AI 无效；从 CPC 上升和 CVR 下降看，主要问题是前端流量变宽后成交承接不足。
- 这组不是继续加预算的问题，优先要收窄低效流量、调整目标，并观察 14-30 天。

### 9.3 多变体 / 结构问题

- 当前不是单个活动表现差，而是不同生命周期或价格带的变体被放进同一套目标里，导致 AI 的预算分配目标冲突。
- 建议把主推款、成长款和清货款拆开托管，让每组目标和行动空间服务同一个业务意图。

### 9.4 上层流量 / 归因

- SB/SD/DSP 这类上层或再营销流量，不能只用 SP 的 last-click ACOS 标准判断全部价值。
- 但如果缺少辅助归因数据，当前只能确认站内直接产出偏弱，建议先降低预算占比或缩小人群。

### 9.5 客户沟通

- 我们先不把这个问题简单归因为 AI，而是拆成流量成本、转化承接和托管边界三层看。
- AI 能做高频调价和预算迁移，但前提是目标、动作空间和活动结构给得对。
- 下一步建议先做小范围设置修复，再用 14-30 天看是否收敛，不建议一次性扩大预算。

## 未开启 AI 推荐 Case

优先推荐：

- 近 30 天有花费、有点击、有订单。
- 花费处于中腰部，或账号花费分布的 50%-90% 分位。
- 订单数建议 >= 5，或销售额 >= 1000 美元/等值货币。
- ACOS/CPA 有压力，或 CPC 上升、CVR 下降。
- 结构清晰，适合 AI 做控价、预算重分配、否定和收割。
- 人工操作频繁但效果不稳定。

暂缓推荐：

- 近 30 天极低花费、无点击、无订单。
- 高花费但完全无销售，且商品承接疑似有问题。
- 极低 ACOS 的稳定品牌词。
- 结构混乱到需要先重建活动。

## Todo 可行性与行动成本

建议动作必须站在客户视角评估是否值得做，不能只给理论最优。每个 todo 必须判断行动成本、预期收益和执行风险，并优先给原托管组内的最小可行改动；只有结构混杂明显或连续 7-14 天修复无效，才建议拆活动、新建托管组或重建架构。

## 7/14/30 天趋势切片

### 5.2.1 7/14/30 天趋势切片

问题 case 不能只看近 30 天汇总。如果 30 天整体达标或接近达标，但截图、周趋势或最近数据出现走差，必须切分 7/14/30 天判断短周期走弱是否已经发生。

执行规则：

- 先看 30 天：判断是否为长期问题、目标错配或结构性问题。
- 再看近 14 天：判断问题是否在最近半月形成趋势，例如 ACOS 抬升、订单下降、CPC 上升、CVR 下滑、预算频繁超限。
- 再看近 7 天：判断是否为短期走弱或预警，例如点击增加但订单下降、花费不降但销售下滑、预算断流、广告位成本突增。
- 如果 7 天和 14 天都走差，即使 30 天汇总尚可，也必须写成「短周期走弱已确认」。
- 如果只有 7 天走差、14 天未验证，写成「短周期预警」，不下长期结论。
- 如果 30 天走差但 7/14 天好转，写成「长期问题仍在，但修复动作开始生效」，建议继续观察而非立即放大改动。
- 不要求每个 case 都展示三个窗口的完整表格，但必须说明为什么选择展示或不展示某个窗口。
