# AI 托管广告 ACOS 与流量质量责任归因报告生成

## 报告目的

按以下优先级回答问题：

1. **流量质量为什么变差？** — 找出异常日期/时段，解释操作如何改变投放时段、广告位置、搜索词和转化效率。
2. **谁导致？** — 用完整操作日志区分 AI、人工和平台系统事件。
3. **怎么修复？** — 给出针对机制的动作、验证指标和回滚条件。
4. **结果有多严重？** — 用简短 KPI 交代 ACOS、CVR、订单、销售额变化。

不要把“CVR 下降，所以 ACOS 上升”当作根因。这只是结果恒等式。报告主体必须继续追问：**为什么同样的点击不再出单，为什么出单词消失，为什么高转化时段失效。**

---

## 报告结构（8 个部分）

```text
1. 标题 + 元信息
2. 背景与分析视角（简短：目标、预算、AI 动作空间、两期范围）
3. 结论（按机制回答流量质量为什么变差，再交代责任）
4. KPI 概览（结果指标 + 能直接支撑机制的指标）
5. Top N 机制问题（按因果贡献排序，而非按指标波动大小排序）
6. AI / 人工 / 系统责任判定
7. 动作建议（针对机制 + 验证 + 回滚）
8. 数据边界 + 一页式通俗结论
```

参考模板：[references/report-template.md](references/report-template.md)。

**篇幅约束：** 背景和结果 KPI 保持紧凑；把主要篇幅放在异常时段 × 操作日志 × 广告数据的交叉验证。禁止为“CVR 下降导致 ACOS 上升”单独铺设长篇章节。

## 核心工作流程

### Step 0：定义对比期并建立数据覆盖清单

- 选取托管开始前的等长时段作为基准期；分析期采用 AI 实际托管的连续时段。
- 从总量重算 ACOS/CVR/CPC，禁止平均每日百分比。
- 记录托管开始/结束时间、目标 ACOS、初始预算、竞价策略，以及 AI 启用的动作空间：竞价分时、预算分时、绩效调价、位置系数、收割、否定、止损等。
- 先列数据覆盖清单，再开始归因：

| 数据层 | 必需内容 | 用途 |
|---|---|---|
| Campaign 日级 | 花费、销售、订单、点击、曝光 | 找异常日和阶段变化 |
| Campaign 小时级 | 两期可比窗口的时段数据 | 找高转化窗口和断档时段 |
| Target 级 | 两期定向表现及当前竞价 | 找问题定向和止损问题 |
| Search term 级 | 两期搜索词、匹配类型、花费、订单、点击 | 判断词池变化与同词 CVR |
| Placement 级（如可用） | 位置 × 时间 × 关键词 | 直接验证位置变化 |
| 操作日志 | 全分析期 + 基准期的 campaign/target/aiGroup | 还原动作、预算轨迹与责任 |

使用 SparkX 时，先读 [references/sparkx-data-retrieval.md](references/sparkx-data-retrieval.md)，遵守实体字段、分页、时区和 ID 规则。

### Step 1：找异常日期和异常时段

**先找变化起点，不要只挑 ACOS 最高的一天。**

- 用日级花费、销售额、订单、点击、CVR、ACOS 标记第一个零销售日、首次持续低 CVR 的起点和行为切换点。
- 把分析期分成行为机制不同的阶段；不要把整个托管期视为同一策略状态。
- 有分时操作或 OOB 时，必须继续做小时级分析。
- 用基准期实际分小时转化曲线定义高转化窗口，不要预设“上午就是高峰”。
- 对比两期可比窗口的总花费，避免把“花得少”误判为“流量质量差”。

```text
异常日 = 连续 3 天 ACOS > 目标 ACOS 且 CVR < 基准期 CVR × 80%
高转化窗口 = 基准期分小时订单和 CVR 共同支持的连续时段
```

详细方法：[references/time-analysis.md](references/time-analysis.md)。

### Step 2：拉全操作日志，通过完整性门禁

**在确认日志完整之前，不得输出“0 次人工操作”“AI 只在某天操作”等结论。**

- 拉取全分析期日志，同时拉取基准期日志作为“正常操作强度”的对照。
- 检查分页结束标志、`truncated`、返回行数上限和实际日期覆盖范围。
- 按日期汇总操作数；若某个早期日期完全无记录，先排除截断，再解释为无操作。
- 用平台可识别的实体 ID 过滤；过滤返回 0 行时先核对 ID 类型，不要直接认定无记录。
- 保留每次操作的时间、对象、原值→新值、操作人和 `operationType`。

### Step 3：围绕异常窗口验证机制假设

把异常日期/时段与操作日志、竞价预算和广告数据放入同一时间线。至少验证以下假设，不要只验证第一个符合直觉的解释：

| 假设 | 必做验证 | 典型结论 |
|---|---|---|
| 竞价时段错配 | 降价/底价操作按小时分布 × 基准高转化窗口 × 同词 CVR | 在高出单时段失去位置 |
| 预算释放错配 | 逐条回放预算上限 × OOB 时刻 × 分小时花费/订单 | 高峰断档、重启后低质消耗 |
| 广告位置变化 | 优先 placement 报表；缺失时用同词 CVR、竞价和时段作间接证据 | 同词流量转化下降 |
| 搜索词池变化 | 共有/新增/消失词、出单词消失、新词 CVR、匹配类型 | 词池漂移或低质词涌入 |
| 否定/暂停误伤 | 否定词与基准出单搜索词逐一交叉核对 | 确认或排除误杀 |
| 高频振荡与止损失效 | 单词竞价轨迹、单日反向调价、零转化持续天数 | 排名不稳、无效花费持续 |

完整验证方法：[references/traffic-quality-mechanisms.md](references/traffic-quality-mechanisms.md)。

### Step 4：建立因果链，区分原因和下游结果

采用以下证据顺序：

1. **时间先后**：操作必须早于或与恶化起点一致。
2. **覆盖一致**：异常窗口与操作作用时段一致。
3. **机制可解释**：操作能解释位置、在线状态、词池或点击质量如何改变。
4. **多源一致**：操作日志、分小时数据、搜索词/位置数据指向同一机制。
5. **反向验证**：寻找策略短暂恢复或 Overshoot 的日期，检查 CVR 是否同步恢复。
6. **排除替代解释**：排查否定词、人工干预、预算总额变化、CPC 变化和正常 broad-match 词池轮换。

不要把“搜索词大量变化”自动当作根因。broad 匹配下，词池翻动可能是竞价/位置不稳定的下游结果。用同词 CVR 和新旧词质量对照判断因果方向。

### Step 5：按“论断”而非按整张图表分级证据

| 等级 | 含义 | 示例 |
|---|---|---|
| A 直接证据 | 数据直接观测到该事实 | 某时点发生 OOB；某小时 AI 将竞价降至 $X |
| B 强支持 | 多个独立证据共同支持 | 预算恢复日 CVR 同步恢复；同词 CVR 多词一致下降 |
| C 间接推断 | 缺少直接维度，只能推理 | 无 placement 数据时推断 Top of Search 丢失 |

同一张图可以包含不同等级的事实。明确写成：“A：已核实的高转化窗口发生底价削减；C：由此推断优质位置流失。”禁止把间接位置推断标成 A。

### Step 6：判定 AI / 人工 / 系统责任

- 将 AI 操作、人工后台操作、Amazon 系统事件分开计数。
- `Campaign Out of Budget` 等平台状态事件不是人工操作；进一步追溯到导致它的预算/竞价策略。
- 人工启用 AI 不等于人工对后续每次自动操作负责；评估初始设置是否合理，再评估人工覆盖和干预。
- 先通过日志完整性门禁，再使用“全部”“0 次”“未发现”等词。

详见 [references/ai-human-attribution.md](references/ai-human-attribution.md)。

### Step 7：针对机制输出建议

每条建议包含：**动作、针对的机制、触发条件、验证指标、观察周期、回滚条件**。

- 竞价时段错配：调整/关闭竞价分时，用高转化窗口订单和 CVR 验证。
- 预算断档：恢复固定预算或设置高峰预算硬约束，用高峰 OOB 次数和在线连续性验证。
- 高频振荡：降低调价频率，用词池稳定性和位置/CVR 验证。
- 止损失效：按连续零转化天数暂停，设定复活条件。

详见 [references/recommendation-format.md](references/recommendation-format.md)。

## 必须回答的质量检查

交付前逐项确认：

- [ ] 是否用主要篇幅解释了流量质量机制，而不是重复 ACOS 算术？
- [ ] 是否验证了日志完整性、日期覆盖和基准期操作强度？
- [ ] 是否找到了异常日期和具体异常时段？
- [ ] 是否把预算/竞价操作按小时与高转化窗口对齐？
- [ ] 是否检查了同一搜索词两期 CVR，而不仅是搜索词数量变化？
- [ ] 是否逐一排除了否定词误杀和人工干预？
- [ ] 是否把位置推断标为间接证据（无 placement 数据时）？
- [ ] 是否明确哪些现象是原因、哪些是下游结果？
- [ ] 是否给出可验证、可回滚的机制修复建议？
